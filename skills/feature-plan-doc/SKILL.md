# feature-plan-doc — 需求落地方案文档

把一个业务需求或改动，落成一份**可直接照抄落地、不允许任何模棱两可说明**的 Markdown 方案文档。核心价值在强制流程：**先理解、先确认、再产出**——绝不在没摸清调用链、没确认设计分叉前就写方案或改代码。

## 何时使用

用户要「方案 / 落地方案 / 改造方案 / 把需求写清楚 / 出 md 方案」，或明确说「先理解我的需求再动手」时使用。

本 skill **只产出一份方案文档**，不修改任何业务代码。修复/落地永远由人在拿到文档后决定。

## 工作流（两阶段，不许跳步）

### 阶段一：先理解，不写代码、不写文档

1. **通读相关代码**：页面、store / 状态管理、工具函数、路由与分流逻辑、跨页透传的上下文。所有关键事实用 `file:line` 引用，不凭记忆、不臆测。
2. **复述理解**：把需求涉及的**完整调用链**按「步骤 / 位置(file:line) / 行为」列成表格，明确标出需求要改的是链路里的**哪一步**。
3. **点出核心难点**：尤其是「跨页 / 跨流程需要新透传什么上下文」这类最易遗漏的点（如：现状只透传了 A，要实现需求必须再透传 B）。
4. **选择题确认设计分叉**：凡是触发范围、实现方式、边界归属等需要用户拍板的分叉，**用选择题问**，每个选项讲清取舍并给推荐项。**不要假设**。
   - 只在真正影响产出的分叉上提问；有合理默认值的直接采用并说明，不滥问。

> 阶段一结束、用户确认理解与选择后，才进入阶段二。

### 阶段二：产出方案文档

输出一份 Markdown 文档，**放在目标工程的 `docs/` 下、文件名用中文**（如 `docs/某某功能改造方案.md`）。

要求：**可直接落地、细节讲清楚、不允许任何模棱两可的说明**。每处改动要精确到「照着抄就能改对」。

## 文档头（每份方案文档必带，置于 H1 标题正下方、正文之前）

H1 标题之后、第 1 节「背景与目标」之前，**必须**插入一段统一文档头：一行说明 + 一张元信息表。**照此格式逐字写**，字段不可删减、不可改名：

```markdown
# <方案标题>

> 本文档由 `feature-plan-doc` skill 产出。仅描述改动，不含已落地代码；落地由人确认后执行。

| 方案模型 | 作者 | 创建日期 | 完成日期 | 状态 |
| --- | --- | --- | --- | --- |
| <出方案的模型名> | lihanqi | <YYYY-MM-DD> | —（审核通过后填写） | 草稿·待落地 |
```

字段填写规则（不许臆造）：

- **方案模型**：当前实际产出本文档的模型名，写清版本，如 `Claude Opus 4.8`、`GPT-5.1` 等。
- **作者**：固定为 `lihanqi`。
- **创建日期**：当天日期。**必须** Read 不到就用 `Bash` 跑 `date +%F` 取真实当天日期（格式 `YYYY-MM-DD`），不要凭记忆写。
- **完成日期**：初始固定写 `—（审核通过后填写）`，**不要**自己填日期——由 `feature-plan-review` 在审核通过时回填。
- **状态**：初始固定写 `草稿·待落地`；后续状态流转（`待修正` / `已审核通过`）由审核环节维护，本 skill 只负责写初始值。

## 方案文档必含章节（缺一不可，文档头之后依次排开）

1. **背景与目标** —— 需求一句话 + 已与负责人确认的设计选择（触发范围、实现方式等逐条写死）。
2. **现状链路** —— 带 `file:line` 的「步骤 / 位置 / 行为」表，标出要改的是哪一步；附关键现状代码片段。
3. **方案总览** —— 改几个文件、机制是什么、为何这样设计（一段话讲清）。
4. **详细改动（逐文件逐处）** —— 每处给「定位现有代码片段」+「改后代码片段」的 **before/after**，带行号定位，精确到可照抄。涉及新增 import / 变量声明 / return 导出的，全部列出，不留「自行补充」。
5. **关键状态 / 标记的完整生命周期** —— 若引入新状态/标记/字段：用表格写死**何时置位、何时消费、何时清理、进程被杀如何**；并把**边界与泄漏风险逐条论证**为「不泄漏 / 可接受」，不许留模糊。
6. **明确不改动项** —— 划清边界，列出哪些文件 / 入口 / 路径**保持原样不动**，尤其加密路径。
7. **已知范围外** —— 与本需求相邻但本次不做的事，写明「现状既有行为，本方案不改」，防止误扩大改动。
8. **验证清单** —— 主场景断言 + 回归断言（不能被破坏的旧路径）；标明哪些**必须真机验证**。
9. **影响文件清单表** —— 文件 / 改动 两列；末尾给**校验命令**（默认 `pnpm type-check`，不跑 build）。

## 硬约束

- **默认不跑 build**：业务代码改动用 `type-check` / `lint` 校验，不用 build「证明可用」。
- **遵守目标工程的 CLAUDE.md / AGENTS.md 全部约定**：先 Read 工程根的约定文件，按其执行（加密红线、状态归属、组件命名分层、样式规范、文件命名、平台脚本注意事项等）。
- **不推荐不存在的组件 / 文件**：引用任何符号名前以实际源码为准。
- **加密 / 签名 / 解密 / 私钥 / 参数拼接路径一律不擅自改**：需改先在文档中指出并要求确认，绝不在方案里替用户决定改加密逻辑。
- **本 skill 不改业务代码**：写文件**仅限** `docs/` 下的方案文档本身。

## 输出后

告知用户文档路径与核心要点（改几个文件、机制、关键边界）。等用户确认后，若用户要求落地，再据文档实施——实施是另一步，不混在出方案阶段里。
